# 取证保留（Forensic Hold）方案说明

## 1. 要解决的问题

一次行李丢失纠纷之后，相关记录已被后来的“整理”（清空队列、压实/压缩日志、重置）
覆盖，现场拿不出原始凭据。本设计为系统增加**对一批记录施加取证保留**的能力，满足：

- 保留期内这些记录既不能被**改写**，也不能被**整理**（压实、清空、重置）；
- 保留范围在施加时**逐条登记、密封并落盘**，事后可逐条复查；
- 释放必须**有依据、经授权**，且与施加人职责分离；存储紧张**不能**成为提前释放的理由；
- 审计链、命令日志、导出三者**逐条咬合**，任意一处被改动都能被发现；
- 受存储成本约束，未被保留的历史可正常压实，且压实不得拖垮常规读写性能。

## 2. 核心对象与不变量

### 2.1 保留清单（HoldManifest）

一次保留请求带来的是“松散范围”（若干行李/航班/审计主体/显式日志序号）。
在**施加那一刻**，系统把范围对照已提交命令日志解析成一份**逐条枚举**清单并冻结：

- `items[]`：每条 = `{sequence, kind, subject, content_hash}`，
  `content_hash = sha256(canonical(kind, payload))`；
- `seal`：对范围、锚点、每一条 `items` 等字段的整体摘要；
- 清单一旦密封，范围**不会随后续整理漂移**，错填一个匹配不到任何记录的 id 会让
  整次施加失败（拒绝“部分保留”这种静默漏保）。

这实现了“保留范围的登记要落盘”：保留本身是一条 `hold.put` 命令，折叠进与其它
命令相同的、带校验和的快照日志（`Store.persist()` 原子写盘），并在施加/延期/释放时
**立即落盘**，不依赖操作员事后手动保存。

### 2.2 不可变闸门（Store guard）

`Store` 在每条命令进入待提交缓冲前调用 `HoldRegistry.vet(kind, payload)`：

- `bag.put`/`flight.put`（改写实体）、`*.remove`、`mapping.put`（重映射）：
  若作用主体落在任一活跃保留的主体集合内，拒绝；
- `recheck.dequeue`、`recheck.clear`、`belt.clear`、`transfer.clear_before`：
  结合当前物化状态做**上下文判断**，只有当真的会清掉被保留主体时才拒绝；
- `reset`：存在任意活跃保留即拒绝。

注意保留是**按范围**生效，不是全局锁：未被保留的行李照常流转，避免“一处取证、全场停摆”。

### 2.3 压实（compaction）

`HoldRegistry.compact(...)` 是唯一允许删除历史的整理路径：

- 活跃保留钉住的序号、所有 `hold.put`、所有 `audit.append` **原样保留**，
  且保留其**原始日志序号**（压缩后日志允许稀疏），因为清单与审计链都按序号引用；
- 被删除的记录折叠进一条 `state.snapshot` 检查点（放在截断水位上），
  并重放校验：压实后的小日志必须重建出与压实前一致的物化状态、且审计链仍然链接，
  否则拒绝接受这次压实；
- 压实动作本身追加一条 `hold.compacted` 审计（删除条数、钉住条数、水位）。

## 3. 释放：依据 + 授权 + 职责分离

- 两类角色：`hold:place`（施加/延期）与 `hold:release`（释放/压实），
  采用 HMAC-SHA256 签名的承载令牌（含主体、角色、签发时间与时效窗口），
  无独立身份服务也能证明“谁在操作”。
- **施加人不得释放同一保留**（职责分离）；伪造或错角色的令牌一律拒绝。
- 释放必须同时提供 `basis`（处置依据，如“案件已审结，文书 CLM-77-9”）
  与 `authorization`（授权文书号），二者为空即拒绝。
- 事件时刻锚定的保留在 `not_before` 之前释放会被拒绝，错误信息明确说明
  **“存储紧张不是依据”**；到期只是“具备释放资格”，仍需上述显式授权动作，
  系统**不会**到点自动删除。
- 释放不是删除：保留记录状态变为 `released`，保留登记、释放依据、释放人与时间
  永久留在日志与审计里，之后是否被压实与“释放”是两件事。

## 4. 保留期起算方式的取舍（含成本来源）

系统支持两种锚点，默认选择**事件时刻锚定**：

| 维度 | `event_time`（事件时刻固定起算，默认） | `matter_close`（调查结束才释放） |
|---|---|---|
| 保留时长 | 有上界：`event_at + retention_days(+延期)` | 无上界，直到显式释放 |
| 证据完整性 | 到期后可能已具释放资格，但仍需授权释放 | 最强，调查期间绝不进入可释放状态 |
| 存储成本 | 可预测、可核算，到期窗口后可回收 | 不可预测，可能无限增长 |
| 适用 | 常规纠纷（可预估处置周期） | 重大/涉诉事项（时长未知） |

**为何默认事件时刻锚定**：题目指出两种方式“在存储成本与证据完整性上的后果相反”。
纯调查结束锚定完整性最强但成本无界；纯固定到期又可能在尚未结案时具备释放条件。
折中为：**以事件时刻锚定的固定窗口作为释放下界**，到期不自动释放、仍须授权；
窗口不够可由 `hold:place` 角色凭依据 `extend` 延期（把下界推后）；重大事项可显式
选用 `matter_close` 获得无界保护。这样完整性不依赖“到点删除”，成本又有明确上界。

**成本来源（写清“钱花在哪”）**，由 `hold-storage`/`/api/holds/storage` 逐条核算：

1. **被钉住的原始日志字节** `pinned_bytes`：保留范围内每条命令的 `kind + payload`
   序列化体量，压实不可回收——这是取证保留的**主要、直接成本**；
2. **永久审计链的体量**：所有 `audit.append` 与 `hold.put` 都不参与回收，
   随每次施加/延期/释放/压实线性增长——这是**可追溯性的固定成本**；
3. **清单与校验哈希的索引成本**：每条 `items` 的序号与 `content_hash`，
   以及重放检查点 `state.snapshot`——这是**换取可逐条复查与快速重放的成本**。

与之对应，`reclaimable_bytes = journal_bytes - pinned_bytes` 给出当前可安全回收量，
按保留（`by_hold[].bytes`）归因，便于对账和容量规划。

## 5. 审计链 / 命令日志 / 导出如何逐条咬合

- **命令日志**：append-only，每条有序号；整体有信封摘要（`Envelope.digest`）。
- **审计链**：每条审计含前一条摘要，形成哈希链（`AuditChain.verify`）；
  施加/延期/释放/压实分别落 `hold.placed/extended/released/compacted`。
- **导出**：`hold/export.py` 产出自描述证据包，内含每条被保留命令的逐字记录与
  `entry_hash`、每份清单及其 `seal`、命令日志头摘要、审计链头摘要，再对这些做
  **包摘要**。`verify_bundle` 离线即可核对：
  - 包摘要 ⇒ 绑定未被重组；
  - 每条记录的 `entry_hash` ⇒ 与清单 `items[].content_hash` 一致；
  - 清单 `seal` ⇒ 范围与枚举未被改动；
  - 审计头摘要与链 ⇒ 审计链完整。

  改动任何一处（篡改一条命令、换一份清单、截断审计）都会使证据包校验失败，
  从而把“审计链—命令日志—导出”三者绑定。

## 6. 性能不塌掉

- 保留判定走物化状态里的清单，闸门是集合命中，常规写入只增加一次 O(1)~O(k) 的
  主体集合判断；
- 压实是**一次性批量操作**，线性扫描日志一次，钉住集合为哈希集合；
  压实后日志更小、重放从检查点继续，常规读取路径反而更轻；
- 被保留数据不额外复制副本（钉住的就是日志里的原始记录），成本只来自
  “本该回收却保留”的那部分字节；
- 冷数据可以在运维层下沉到廉价存储（本服务只暴露字节数与可回收量，不替容量决策），
  但**任何下沉/回收都不能提前释放活跃保留**。

## 7. 接口一览

- 命令行（`python -m bagsort`）：
  `hold-token`、`hold-place`、`hold-list`、`hold-storage`、`hold-extend`、
  `hold-release`、`hold-verify`、`compact`。
- HTTP：
  `POST/GET /api/holds`、`GET /api/holds/{id}`、
  `POST /api/holds/{id}/extend|release`、
  `GET /api/holds/{id}/records|verify|export.csv`、
  `GET /api/holds/storage`、`GET /api/holds/export`、
  `POST /api/holds/export/verify`、`POST /api/store/compact`。
- 凭证可通过 `Authorization` 头或请求体 `credential` 字段提交。

## 8. 边界与取舍

- 保留只能保护**施加时已存在**的记录；施加之前已被物理删除的历史无法找回。
- 事件时刻不得晚于当前合成时钟；`matter_close` 保留没有 `not_before`，也不能延期。
- 释放只改变保留状态；真正回收历史要等后续一次经授权的 `compact`。
- 凭证为对称 HMAC，密钥经 `Plant.build(hold_secret=...)` 注入，默认值仅用于开发/测试，
  生产应通过部署配置注入。
